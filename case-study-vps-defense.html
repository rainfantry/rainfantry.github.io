Defense Layers: How to Secure Your Server

Security isn't one thing — it's layers. Each layer stops different attacks. Here's what we run:

Defense Stack
Click to expand
🔑
SSH Key-Only Authentication
Disable password login entirely. Use cryptographic keys that can't be guessed.
ENABLED
Why it matters: Password brute-force attacks try thousands of combinations. With key-only auth, there's no password to guess — attackers need your private key file, which never leaves your computer.
/etc/ssh/sshd_config
PasswordAuthentication no PubkeyAuthentication yes PermitRootLogin prohibit-password
🚫
Fail2ban Auto-Banning
Automatically block IPs that fail login attempts. 3 strikes = 1 hour ban.
ENABLED
Why it matters: Even with strong passwords, letting attackers try forever is risky. Fail2ban watches log files and temporarily blocks IPs that fail authentication — stopping brute-force attacks in their tracks.
Commands
# Check banned IPs fail2ban-client status sshd # Manually ban an attacker fail2ban-client set sshd banip 8.209.215.33
🔥
UFW Firewall
Block all ports except the ones you explicitly need (22, 80, 443).
ENABLED
Why it matters: By default, Linux accepts connections on any port. A firewall flips this — deny everything, then allow only what you need. If you're not running MySQL, close port 3306. Don't give attackers extra doors to try.
Setup
ufw default deny incoming ufw default allow outgoing ufw allow 22/tcp # SSH ufw allow 80/tcp # HTTP ufw allow 443/tcp # HTTPS ufw enable
🍯
Honeypot Monitoring
Fake services on attack ports that capture attacker behavior and alert you.
ENABLED
Why it matters: Honeypots give you visibility into what attackers are trying. When someone connects to port 4444 (Metasploit default), you know someone's probing for reverse shells. This intel helps you understand the threat landscape.
📊
Log Monitoring
Regular review of auth.log, fail2ban.log, and connection logs.
ENABLED
Why it matters: Defenses are useless if you never check them. Regular log review shows you attack patterns, helps you tune your rules, and catches anything that slipped through.
Quick Security Check
# Recent failed SSH attempts grep "Failed password" /var/log/auth.log | tail -20 # Who's connected right now ss -tn state established # Recent fail2ban bans tail /var/log/fail2ban.log | grep Ban

Key Takeaways

✓ Every server gets attacked. It's not personal — bots scan every IP. Assume you're being probed 24/7.
✓ SSH keys > passwords. No password is strong enough against endless brute-force. Key-only auth stops 99% of SSH attacks.
✓ Fail2ban is essential. Auto-banning failed logins is the minimum viable security. Takes 5 minutes to set up.
✓ Close unnecessary ports. If you're not running a service, close the port. Fewer doors = fewer attack vectors.
✓ Honeypots provide intel. Knowing what attackers try helps you prioritize defenses.
✓ Check your logs. Automated defenses work, but human review catches edge cases.
